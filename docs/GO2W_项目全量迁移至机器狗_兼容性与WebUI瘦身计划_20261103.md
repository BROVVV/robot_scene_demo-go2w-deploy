# GO2-W 项目全量迁移至机器狗计划书

> 版本：2026-11-03  
> 目标：把当前主要运行在 Ubuntu x86 控制电脑上的感知、遥操建图、语义搜索、导航、Web 后端等组件迁移到 Go2-W 内部 Jetson；电脑最终只保留浏览器 WebUI。迁移后必须保持项目现有功能等价，尤其保证遥操建图和自主搜索两条主链可用。第一阶段明确停用 WebUI 3D 点云显示及点云网络传输。  
> 本文是迁移与验收计划，不授权真实运动，也不直接覆盖机器狗现有部署。

> **2026-11-04 用户范围修订（优先于下文原始范围）**：机器狗当前只建二维地图，停用三维点云地图累计、RGB-LiDAR 三维融合、辅助点云发布与三维 LIO 输入转发；保留将机身雷达原始输入转换为二维扫描所必需的处理，以及原有地面验证、避障、新鲜度和运动安全判断。WebUI 使用独立二维栅格接口和画布。恢复三维建图须另获用户明确要求，不得在后续迁移阶段自动恢复。该运行档仅作用于机器狗候选部署，电脑原项目应始终保持可运行。

> **2026-11-09 用户时长修订（优先于下文原始验收时长）**：用户要求“30分钟也太长了，短一点差不多测试一下就够了”。本轮及后续现场抽检采用约1–3分钟的短时验证，不为原计划中的30分钟、30–60分钟等待而延迟迁移；长期稳定性仅保留为未测范围。必须保留短时采样中实际发现的异常，缩短测试不代表消除异常，也不改变运动授权、故障停车和其他功能要求。

> **2026-11-10 用户供电指令补充**：用户要求“继续工作，直到5的电量再停”。后续静止部署、编译和隔离测试在连接可用、能获取新鲜电量时按5%停止线安排，持续保存进度；既有真实运动电量/现场安全门保留。用户随后确认机器狗正在充电，要求先进行电脑端测试；充电期间按该最新分支执行，不根据历史电量自动恢复真机作业。

## 1. 执行摘要

本次迁移可行，但不能把电脑上的整个目录、虚拟环境、ROS `build/install` 或 CUDA/PyTorch 包直接复制到机器狗。两端的操作系统、CPU 架构、ROS、Python、CUDA 和 GPU 软件栈均不同，必须采用以下原则：

1. 只迁移源码、配置、模型和经过筛选的数据，不迁移 x86 二进制、虚拟环境和构建产物。
2. ROS 以机器狗原生 ROS 2 Foxy + Python 3.8 为基线，在机器狗上重新构建。
3. Web/业务 Python 使用独立 Python 3.8 虚拟环境；ROS Python 使用系统 `/usr/bin/python3`，二者不混装。
4. GPU 推理使用与 JetPack 5.1.1、CUDA 11.4、aarch64 匹配的 Jetson 包或容器，禁止使用电脑上的 `cu121`/x86 wheel。
5. 机器狗现有 `/home/unitree/robotscene` 有大量未提交修改，必须先完整归档，再旁路部署到新目录，不得原地覆盖。
6. WebUI 第一阶段不启动点云 Web bridge、不提供 `/api/slam/map3d`、不加载点云 JavaScript、不渲染点云画布。
7. 按 2026-11-04 修订，机器狗仅保留二维扫描生成所需的原始雷达处理，不进行三维点云建图；二维 SLAM、导航和避障安全链继续保留。
8. 电脑最终通过 `http://<机器狗无线IP>:8765/` 访问 WebUI；ROS DDS 不通过 Wi-Fi 跨机广播。
9. 迁移采用功能等价门：除用户明确要求暂时停用的三维链路外，任何现有功能都不能静默降级；遥操二维建图、自主搜索、相机、检测、VLM、2D 拓扑、回放、急停和运动安全链都必须逐项验收。

### 1.1 不可退化功能基线

迁移完成不以“进程能启动”或“网页能打开”为完成标准。以下功能是 production cutover 前必须保持的基线：

| 功能域 | 必须保留的能力 | 允许的变化 |
| --- | --- | --- |
| RGB-D | D435 彩色、深度、内参、帧新鲜度、3D 目标定位 | 浏览器视频可降分辨率/帧率；内部深度数据不能因 Web 瘦身被删除 |
| LiDAR/SLAM | 本地 LiDAR、时间同步、里程计、SLAM、2D 占据地图、定位健康门 | 不向浏览器传输 3D 点云；内部 PointCloud2 仍可使用 |
| 遥操建图 | 一键启动/停止/丢弃会话、遥控器驾驶、语义侧车、YOLOE/VLM、对象记录、2D 地图/拓扑、日志和录像 | WebUI 不显示 3D 点云；录像从三路改为相机+2D 拓扑两路 |
| 自主搜索 | 自然语言任务、目标理解、检测与复核、目标 3D 定位、Nav2 规划/执行、暂停/恢复/停止/急停、历史和回放 | WebUI 不显示 3D 点云；搜索内部仍使用地图与几何证据 |
| 手动控制 | WebSocket 控制、控制权仲裁、命令看门狗、停止与急停 | 不能因 Web 与 ROS 同机而绕过仲裁 |
| 运动安全 | 唯一 action server、唯一 odom、九道速度闸门、实体遥控监督、fail-closed | 不允许为了单机部署减少任何安全门 |
| WebUI | 实时相机、目标框、状态、2D 语义/导航拓扑、事件、历史、回放、系统状态 | 明确移除 3D 点云区及其网络请求 |
| 数据与取证 | session、events、决策、对象图、地图元数据、日志、录像、错误码 | 路径可迁移到 runtime 目录，但语义和保留策略不变 |

用户在 2026-11-04 明确要求停用三维建图及辅助点云链路，这是当前批准的范围裁剪。任何其他能力若因 Foxy、aarch64 或资源限制无法实现，必须显式报为 blocker，并回滚到上一阶段，不能用“降级可运行”替代功能等价。

## 3. 当前迁移阻塞点

### 3.1 不能直接复制的内容

以下内容必须排除：

- `.venv/`、`.runtime_venv/`、`.yoloe_env/`；
- ROS `build/`、`install/`、`log/`；
- `__pycache__/` 和 `.pyc`；
- x86_64 原生二进制和 Node 原生模块；
- `torch==2.5.1+cu121`、`torchvision==0.20.1+cu121`；
- 电脑生成的 CUDA/TensorRT engine；
- 电脑上的 CycloneDDS 网卡配置；
- 未筛选的历史 `outputs/`、rosbag、日志和缓存。

原因是这些文件绑定 x86_64、Ubuntu 22.04、Python 3.10/3.11/3.13、ROS Humble 或 CUDA 12.1，无法在 aarch64/Foxy/CUDA 11.4 上可靠运行。

### 3.2 Python 依赖没有锁定

根目录 `requirements.txt` 当前基本没有版本约束。电脑已经出现 NumPy 2.x、OpenCV 5、FastAPI 0.14x 等较新组合，而机器狗 Python 3.8 不能直接使用这些最新版本。

机器狗现有 `.runtime_venv` 的已知组合为：

- FastAPI 0.103.2；
- Uvicorn 0.23.2；
- websockets 11.0.3；
- Pydantic 2.8.2；
- 系统 NumPy 1.17.4、SciPy 1.3.3、OpenCV 4.2.0。

源码审计覆盖 789 个 Python 文件，Python 3.8 语法解析错误为 0，因此优先保留 Python 3.8，而不是为了业务代码升级机器狗系统 Python。迁移前需要创建并验证专用锁文件：

```text
requirements/robot-py38.in
requirements/robot-py38.lock
requirements/robot-ml-jetpack51.lock
```

锁文件必须在 aarch64/Python 3.8 环境内解析并用 `pip freeze` 固化，不得直接复用电脑锁文件。

### 3.3 机器狗用户目录存在损坏的 PyTorch

机器狗当前从 `~/.local/lib/python3.8/site-packages` 导入 PyTorch 时出现本地动态库错误。迁移过程必须：

- 所有服务设置 `PYTHONNOUSERSITE=1`；
- 不在系统 Python 中继续 `pip install --user`；
- ROS 使用系统包，Web 使用独立 venv，ML 使用单独 venv/容器；
- 验证环境时打印 `sys.executable`、`torch.__file__`、CUDA 可用性和架构。

### 3.4 ROS Humble 与 Foxy 差异

机器狗真实 ROS 版本是 Foxy。`/opt/ros/humble` 仅为 Foxy 的软链接，不能据此把机器狗当成 Humble。

需要处理：

- 启动脚本中硬编码的 `/opt/ros/humble`；
- `nav2_params_humble.yaml` 中的 Nav2 插件名、BT 节点、参数结构；
- Humble 才有的 Nav2 Collision Monitor、Velocity Smoother 行为差异；
- Foxy Nav2 0.4.7 与 Humble Nav2 的 action、lifecycle 和默认 BT 差异；
- ROS Python 必须使用 `/usr/bin/python3.8`，不能由 Web venv import `rclpy`；
- C++ ROS 包必须在机器狗上以 Foxy underlay 重新 `colcon build`。

迁移目标不是伪装 Humble，而是新增明确的 Foxy 配置：

```text
configs/ros/foxy/
ros2_ws/src/robot_scene_nav_bringup/config/nav2_params_foxy.yaml
scripts/go2w/build_ros2_foxy.sh
```

### 3.5 GPU/ML 兼容与资源约束

当前电脑的 YOLOE 环境依赖 CUDA 12.1 的 PyTorch wheel，不能安装到 Jetson。机器狗必须使用与 JetPack 5.1.1/CUDA 11.4 匹配的 NVIDIA aarch64 PyTorch，或使用匹配 L4T 的 GPU 容器。

同时，仓库中的模型体量包括：

- RAM++ checkpoint 约 3.0 GB；
- GroundingDINO checkpoint 约 694 MB；
- BERT 权重约 440 MB；
- SAM2 tiny 约 156 MB；
- YOLOE-Seg 权重约 31–40 MB。

Orin NX 只有 16 GB 共享内存，不能默认同时常驻 RAM++、GroundingDINO、SAM2、YOLOE、SLAM、Nav2 和 Web 服务。第一阶段建议只启用一个本地视觉后端：

1. 优先评估 YOLOE-Seg 小模型的 Jetson/TensorRT 路线；
2. Grounded-SAM 作为按需低频进程，不能默认常驻；
3. RAM++ 暂不进入第一阶段常驻部署；
4. VLM 继续使用远程 API 或低频守护进程；
5. 每个后端必须分别测量显存/共享内存、FPS、温度和功耗后才能组合。

### 3.6 硬件端口和传感器网络

截至本计划本次更新，机器狗上的无线网卡已经拔下，D435 RGB-D 相机已经重新插回。扩展坞到位前，迁移与验收继续使用千兆网线，不能把“无线已配置”作为当前硬件状态假设。

后续机器狗要同时运行本地视觉和无线 WebUI，必须先解决物理连接：

- 使用稳定的有源 USB 3.x 扩展坞/Hub 同时连接 D435 与无线网卡；或使用 Jetson 另一独立 USB 3 端口；
- 扩展坞必须有足够供电，不能只依靠 Jetson 单口为 D435 和无线网卡同时供电；
- 优先让 D435 使用 SuperSpeed 5 Gbit/s 链路；用 `lsusb -t` 验证不是 480 Mbit/s USB 2；
- 检查 D435 和无线网卡是否共享同一个 USB root hub；若共享后出现掉帧/掉线，应改用不同 root hub 或降低视频参数；
- 同时验证 D435 彩色流、深度流、相机内参和 Wi-Fi 持续吞吐，不能只验证设备能被 `lsusb` 看到；
- 进行至少 30 分钟 D435+Wi-Fi 并发浸泡，记录相机 FPS、USB 错误、无线丢包和内核日志；
- 扩展坞验收通过前，生产操作保留网线，不执行“拔网线仅无线运行”的最终切换。

外置 PandarXT-16 若继续使用，应通过千兆小交换机与机器狗 `eth0` 组成本地传感器网。为同时保留电脑原项目的实时收流能力，当前已将 Hesai UDP 目标设为组播 `239.192.0.20:2368`，电脑 `192.168.123.99` 与机器狗 `192.168.123.18` 分别加入该组；两端的 20 帧只读点云验收均通过。若组播链路退化，可恢复原电脑单播 `192.168.123.99:2368`，并保持机器狗迁移入口封锁。如果现场只使用机身 LiDAR，则应明确禁用 Pandar 依赖，而不是让相关节点等待不存在的数据。

## 4. 目标架构

```text
机器狗 Jetson Orin NX
├─ ROS 2 Foxy 系统环境（/usr/bin/python3.8）
│  ├─ Unitree 状态与运动安全链
│  ├─ 相机/LiDAR 驱动与时间同步
│  ├─ LIO/SLAM/Nav2
│  └─ ROS sidecar：仅输出结构化状态和 JPEG 帧
├─ Web/Core venv（Python 3.8，PYTHONNOUSERSITE=1）
│  ├─ FastAPI/Uvicorn
│  ├─ WebSocket 控制与状态
│  ├─ 语义搜索、任务规划、记忆与日志
│  └─ WebUI 静态资源
├─ ML venv 或 Jetson GPU 容器
│  └─ YOLOE 或按需 Grounded-SAM 推理服务
└─ 本地 IPC
   ├─ loopback HTTP/Unix socket
   ├─ 原子 JSON/JPEG 快照
   └─ 必要的本机 ROS topic

Wi-Fi
└─ 电脑浏览器
   ├─ MJPEG 或后续 WebRTC/H.264 视频
   ├─ WebSocket 状态和控制
   ├─ 2D 语义/导航拓扑
   └─ 不接收 3D 点云
```

ROS DDS 应优先绑定机器狗本地传感器接口/loopback，不在 Wi-Fi 上广播大体量 ROS topic。Web 服务绑定 `0.0.0.0:8765`，由浏览器通过 `wlan0` 访问。

## 5. WebUI 3D 点云暂时移除方案

### 5.1 功能边界

第一阶段保留：

- 实时相机画面；
- D435 深度采集和目标 3D 定位能力；
- 目标框/分割或识别结果；
- 机器人状态、任务状态、急停和控制；
- 2D 语义拓扑与导航拓扑；
- 事件时间线、历史任务和日志；
- SLAM/定位健康状态的文字与指示灯。
- 遥操建图和自主搜索内部使用的 LiDAR、SLAM、地图、TF 与几何证据。

第一阶段移除：

- 3D 点云 canvas；
- 当前 scan 调试层；
- `/api/slam/map3d`；
- `slam_map_3d.js` 的周期轮询；
- `plain_slam_web_bridge.py`/`nav2_web_map_bridge.py` Web 点云 sidecar；
- `slam_map_3d.json`、`slam_map_meta.json` 的 Web 点云快照生成；
- 浏览器三路录像中的 3D 地图通道。

内部 SLAM/LiDAR topic 不删除，避免破坏定位、导航与安全链。

“不传 3D 点云”只约束浏览器/Web 网络边界，不能把以下内容误删：

- 遥操建图所需的本地 LiDAR→SLAM→2D 栅格/语义对象链；
- 自主搜索所需的地图、TF、定位、局部障碍与 clearance 证据；
- D435 深度图和相机坐标系下的目标 3D 定位；
- 离线保存地图、对象记录和事故取证所需的本地数据。

### 5.2 建议采用功能开关而不是删除源码

新增：

```dotenv
GO2W_WEB_3D_MAP_ENABLED=0
GO2W_WEB_POINTCLOUD_BRIDGE_ENABLED=0
```

默认在机器狗 profile 中关闭。未来需要恢复 3D 显示时可以重新开启并单独验收，不需要从历史版本复制代码。

### 5.3 需要修改的代码位置

| 文件 | 修改内容 |
| --- | --- |
| `scripts/go2w/start_autonomous_search_web.sh` | 开关为 0 时不启动任何点云 Web bridge，不创建 PID 文件和快照路径 |
| `app/manual_web_demo/web_server.py` | 禁用或不注册 `/api/slam/map3d`；状态接口明确返回 `web_3d_map_enabled=false` |

| `tests/test_plain_slam_webui_3d.py` | 改为验证关闭状态不启动桥、不轮询、不生成快照 |

| `scripts/go2w/start_remote_control_mapping.sh` | 关闭 Web 点云 writer，但保留 2D SLAM、语义 mapper、YOLOE/VLM 和 session 产物 |

### 5.4 视频带宽控制

当前 D435 HTTP 服务为 1280×720@30 FPS MJPEG。迁移后建议第一阶段改为：

- 640×480@15 FPS，JPEG quality 60–75；或
- 1280×720@10–15 FPS，仅在识别/复核时提高帧率；
- 浏览器只建立一个实时视频连接，其他组件复用机器狗本地帧；
- 目标 WebUI 视频带宽 3–8 Mbit/s；
- 第二阶段再评估 WebRTC/H.264，将延迟和带宽进一步降低。

## 12. 回滚方案

出现以下任一情况立即回滚：

- ROS graph、TF 或时间戳异常；
- Nav2 Foxy 行为与基线不一致；
- 内存接近耗尽、持续 swap、GPU Xid 或热降频；
- WebUI 仍产生点云传输；
- Wi-Fi 频繁断流或控制延迟超阈值；
- 急停、看门狗、控制仲裁任一项不通过；
- 新服务修改了机器狗底层固件或厂商服务行为。

回滚动作：

1. 触发软件急停并确认物理停止；
2. 停止新 release 的 systemd units；
3. 切回上一个 `robotscene_current`；
4. 恢复旧 EnvironmentFile 和服务；
5. 验证运动服务、相机和网络基线；
6. 保存新 release 日志，不原地修补生产目录。

## 15. 本计划的推荐决策

推荐采用“机器狗单机运行 + 电脑纯浏览器”的最终架构，但分两步完成：

1. 先完成 Web/Core、ROS Foxy、相机和轻量视觉后端迁移，关闭 WebUI 3D 点云；
2. 再根据 Orin NX 的实测资源决定是否把 Grounded-SAM/RAM++ 全部常驻到机器狗。
