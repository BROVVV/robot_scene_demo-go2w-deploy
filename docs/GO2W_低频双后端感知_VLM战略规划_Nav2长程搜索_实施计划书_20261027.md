## 3. 当前问题与目标结构

当前自主搜索循环的问题是：检测、VLM 和局部移动耦合得太紧。一次较短移动后又进入观察和复核，导致慢速 VLM 被频繁调用，而 `nav2_candidate_geometry.py` 中约 `0.50 m` 的常规前沿截断又放大了这一问题。

改造后的职责边界应为：

```text
相机关键帧
   │
   ├─ 本地检测器：Grounded-SAM 或 YOLOE（低频/事件触发）
   │
   └─ VLM 战略复核（只在战略决策点调用）
          │
          ├─ 当前视角有目标：选择检测候选并进入目标复核/接近
          │
          └─ 当前视角无目标：在给定的可达候选 ID 中排序
                         │
                         ├─ 前沿观察点
                         ├─ 路口/分岔观察点
                         └─ 语义上更可能的已知区域
                                      │
                                      ▼
                         Nav2 长程规划、绕障和执行
                                      │
                                      ▼
                       到达/失败/发现目标后再做战略决策
```

高频安全闭环仍由激光雷达、代价地图、Nav2 controller 和现有安全逻辑负责。VLM 不参与实时避障，也不持续输出运动指令。

## 4. 目标行为规格

### 4.1 本地检测触发规则

仅对自主搜索中的本地结构化检测后端应用以下统一调度。Grounded-SAM 和 YOLOE 使用完全相同的规则。

满足任一条件时允许产生一次新检测：

- 自主搜索启动后的首个稳定关键帧。
- 距上次检测达到约 `3 s`。
- 机器人累计平移达到约 `0.8 m`。
- 机器人累计转向达到约 `30°`。
- 到达战略目标点并稳定。
- Nav2 任务失败、被取消或发生明显重规划失败。
- 到达新的路口/分岔观察点。
- 地图切换到新的 place/region，确实需要更新语义证据。

实现要求：

- “走几步”统一用里程计平移距离表示，不绑定机器狗具体步态。
- 转角使用自上次实际检测以来的累计 yaw 变化，不能只依赖当前朝向所在扇区。
- 设置约 `1 s` 的最小去抖间隔，避免多个条件同一时刻造成重复推理。
- 调度未触发时复用最近一次带时间戳和位姿的检测结果，不重复调用模型。
- 每次真实推理后同时更新检测时间、检测位姿和累计转角基准。
- 不在 planner tick、controller tick 或每次状态轮询中调用检测器。

优先扩展现有 `app/perception/detection_scheduler.py`，不要另造调度框架。

### 4.2 一帧只做一次本地全图检测

当前本地结构化后端可能在前台目标检测之外，又为后台完整语义观察执行一次 `slots=None` 的全图推理。本次必须消除同一关键帧上的重复本地检测：

- 一次全图本地检测结果同时供目标候选、场景物体、语义记忆和可视化使用。
- 需要按 target/anchor/scene 分类时，在同一结果上筛选，不再次运行模型。
- Grounded-SAM 与 YOLOE 都遵守该规则。
- 缓存键继续包含后端、模型、帧身份和必要的 prompt/term 信息，不能跨后端误用结果。
- VLM 战略观察不是本地检测的第二次替代调用，两者职责不同；VLM 只在第 4.3 节规定的时机运行。

### 4.3 VLM 战略复核

VLM 只在以下战略决策点调用：

- 启动后首个稳定视角。
- 到达一个长程战略目标点。
- Nav2 无法到达当前战略目标，需要换方向。
- 本地检测器发现高置信度目标候选，需决定是否中断当前导航。
- 当前战略意图已完成或地图变化使原目标失效。

不要因为普通局部路径更新、临时绕障或短暂减速调用 VLM。

VLM 一次请求应接收：

- 当前稳定 RGB 图像。
- 用户目标名称和已有目标描述。
- 当前本地检测器的候选摘要及稳定 ID。
- 程序提前生成并确认可达的前沿/路口候选 ID、相对方向、距离。
- 可选的 place/room 语义记忆摘要。
- 已访问和最近失败候选的简短摘要。

VLM 只返回结构化战略判断：

```json
{
  "target_state": "present | possible | absent | unknown",
  "target_detection_id": "可为空，只能引用输入中的检测 ID",
  "selected_search_candidate_id": "可为空，只能引用输入中的可达候选 ID",
  "reason": "一句简短理由"
}
```

限制：

- VLM 不得生成坐标、速度、角度、步数、`cmd_vel` 或运动脚本。
- VLM 不得选择输入列表之外的 ID。
- `present/possible` 且引用了有效检测 ID 时，进入现有目标验证/接近流程。
- `absent` 时，采用它选择的可达战略候选。
- `unknown`、超时或返回无效 ID 时，只执行一个简单确定性规则：从程序已排序的可达候选中取第一项。不要为此新增多层 fallback 系统。
- 若 VLM 认为画面有目标但没有本地检测框，只记录为 `possible`，停止稳定后触发一次新的本地检测；不得根据 VLM 自造目标坐标。

实现时优先复用现有 VLM daemon/client 和现有 `semantic` 请求能力，在现有响应中增加可选战略字段，或在 `run_semantic_exploration.py` 中增加一个聚焦函数。除非现有协议确实无法承载，否则不要新增 daemon、长期服务或第二套 VLM 客户端。

### 4.4 搜索候选与路口候选

程序先生成候选，VLM 只负责排序。候选至少包括：

- 可达前沿观察点。
- 路口/分岔观察点。
- 现有空间推理器认为与目标更相关的已知区域观察点。

路口/分岔检测保持轻量：

- 基于现有占据栅格和可达前沿的方位聚类。
- 当同一局部区域存在至少两个明显分离的自由空间方向，可视为分岔候选；建议方向间隔不小于约 `45°`。
- 返回位于已知自由空间内、具有足够 clearance 的观察点，不把目标放进未知栅格。
- 可新建一个小型 `app/spatial/junction_extractor.py`，返回与现有前沿候选兼容的字典/对象，并用 `source="junction"` 标记。
- 不实现完整拓扑 SLAM、骨架图框架或新的地图数据库。

候选排序的程序基础分应继续考虑：

- 可达性和 Nav2 路径长度。
- 未探索收益。
- 路口的多方向可观测性。
- 与目标语义先验的相关度。
- 最近访问/失败惩罚。

VLM 的选择只作用于已经通过可达性和安全检查的候选，不覆盖硬约束。

### 4.5 长程目标与 Nav2 执行

改掉正常搜索中的固定 `AUTONOMOUS_FRONTIER_HOP_M = 0.50` 截断语义：

- 对已知自由空间内的候选，优先生成约 `1.5–3.0 m` 的战略目标，实际上限服从现有 profile 的最大步长、地图边界、clearance 和 Nav2 可达性。
- 对未知空间边缘，不把 goal 放进未知区；目标放在已知自由空间内，距未知边界保留约 `0.6–1.0 m` 的观察距离。
- 当已知自由路径确实不足时，才允许退化为约 `0.5 m` 的短目标。
- 若长路径需要 Nav2 内部生成多个控制段，不重新调用 VLM。
- 若只能逐段到达，同一战略意图可以跨越多个 Nav2 子目标保持有效；只有到达战略观察点、目标失效或导航失败才重新决策。

Agent 输出示例：

```json
{
  "intent": "inspect_frontier | inspect_junction | approach_target",
  "candidate_id": "frontier_3",
  "reason": "右侧房间更可能包含目标"
}
```

随后由程序把候选 ID 解析为经过校验的地图位姿，交给现有 Nav2 backend。Nav2 继续负责：

- 全局路径规划。
- 局部避障。
- 速度控制。
- 短时动态障碍处理。
- 现有恢复行为和安全停止。

不得让 LLM/VLM 绕过 Nav2 直接发布 `/go2w/motion`、`cmd_vel` 或等价控制消息。

### 4.6 导航中断规则

Nav2 执行长程目标期间：

- 安全传感器和 Nav2 持续正常运行。
- 本地检测调度仍可按时间/距离/转角触发，但不得阻塞 controller 高频循环。
- 若检测到高置信度目标候选，取消当前战略 goal，安全停止并等待画面稳定，再做一次 VLM/目标验证。
- 普通低置信度物体或场景更新只记入最近观测，不打断导航。
- Nav2 的普通局部重规划不触发战略 VLM。
- Nav2 最终失败才触发新的候选选择。

## 6. 实施顺序

以下顺序用于保证任何中间状态都不破坏遥控器被动建图。

### 阶段 0：建立边界，不改运行系统

1. 记录当前 `git status`，把所有已有修改视为用户资产。
2. 确认本次只修改第 5 节允许范围内的文件。
3. 确认冻结文件没有进入待修改列表。
4. 检查是否存在正在运行的被动建图进程；只观察，不停止、不重启。
5. 不连接 SSH 修改机器狗系统，不部署，不触发真实运动。

完成条件：已经确认自主搜索与被动建图的文件、进程和输出目录边界。

### 阶段 1：统一双后端检测调度并消除重复推理

1. 扩展现有 `DetectionScheduler`，加入平移、累计转角和事件触发。
2. 在自主搜索主循环中只通过这一入口决定是否推理。
3. 将一次本地全图检测结果同时交给目标候选和语义观察。
4. 保持 `grounded_sam`、`yoloe_seg` 使用同一调用路径。
5. 日志记录 `backend`、`trigger_reason`、帧 ID、距离、转角和距上次推理时间，便于验收；不要增加复杂 telemetry 系统。

完成条件：同一后端、同一帧、同一术语集合不再发生重复全图检测；普通循环不会每步调用检测器。

### 阶段 2：加入战略 VLM 和候选约束

1. 复用现有 VLM 调用链，形成第 4.3 节的结构化结果。
2. 给所有可达候选生成稳定 ID。
3. 加入轻量路口候选。
4. 严格校验 VLM 只能引用输入 ID；无效结果直接使用程序排序第一项。
5. 将目标出现、未出现和未知三种结果接入现有状态流。

完成条件：VLM 不返回底层动作；当前视角无目标时能在前沿、路口或语义区域中选出一个程序已验证的候选。

### 阶段 3：改成长程 Nav2 战略目标

1. 移除 `0.50 m` 作为正常搜索上限的行为。

## 8. 验收标准

全部满足才算完成：

- 遥控器被动建图的启动脚本、停止脚本、worker、配置和 passive watch 无 diff。
- 被动建图的 `grounded_sam` 与 `yoloe_seg` 两个 smoke 均通过，或因现有进程资源冲突未执行时明确记录，绝不伪报。
- 自主搜索仍可通过参数明确选择 `grounded_sam` 或 `yoloe_seg`。
- 两个后端共用同一套 cadence、VLM 战略决策和 Nav2 长程规划逻辑。
- 同一关键帧不会为了目标检测和语义观察重复跑一次本地全图检测。
- 普通导航循环不会每走一个短步调用一次 VLM。
- VLM 只在启动、战略到达、导航最终失败或发现目标等关键事件调用。
- 当前视角没有目标时，系统能够选择一个可达前沿、路口或语义区域候选。
- Agent/VLM 只返回意图和候选 ID，不返回或发布底层运动控制。
- 已知自由空间足够时，正常战略 goal 可达到约 `1.5–3.0 m`，不再固定为 `0.5 m`。
- 未知前沿目标仍位于已知自由空间内，并保留观察距离。
- Nav2 仍负责全局规划、局部避障、控制和原有安全行为。
- 只增加必要配置和测试，没有新建无必要的框架、服务或大规模重构。

## 9. 建议日志与效果判断

只需在现有事件日志中补充少量字段：

```json
{
  "detector_backend": "grounded_sam | yoloe_seg",
  "detection_trigger": "initial | time | translation | rotation | arrival | nav_failure | target_candidate",
  "strategic_candidate_id": "frontier_3",

```

用一次短时 dry-run 或受控运行比较以下指标即可：

- 本地检测调用次数。
- VLM 调用次数。
- 同帧重复检测次数，应为 `0`。
- 每次战略 VLM 决策之间的实际导航距离。
- 长程 goal 的距离分布。
- Nav2 成功、失败和因目标发现而中断的次数。

不需要新建指标平台。验收重点是：VLM 调用次数显著下降，同时没有降低目标复核、导航安全和双后端可用性。
