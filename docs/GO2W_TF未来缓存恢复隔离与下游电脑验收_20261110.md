# TF未来缓存恢复隔离与下游电脑验收（2026-11-10）

承接TF异常时间戳本地缓冲修复。本轮按用户要求继续电脑测试，全部为Humble、Domain98、localhost-only。未连接机器狗、未部署源码、未创建真实Action客户端或SDK对象，也未调用云端API。机器狗端状态仍以上一次遥端记录为准，本轮不假定已充电或重启。

## 下游缺口实际复现

上一轮的TimestampGuardedBuffer避免了健康节点自身保留异常未来位姿，但不能清除别的进程中普通tf2缓冲里的数据。本轮增加独立普通Buffer/TransformListener，并调用实际 `create_nav2_search_backend(..., dry_run=True, tf_buffer=...)` 的get_pose读取路径。仅Action端口替换为遇到send立即失败的测试对象，不替换位姿读取或TF算法。

相同“时间戳超前2秒、位置偏移10厘米，然后恢复正常流”的组合故障中，健康节点本地位姿已正确，实际搜索后端仍在3个健康为true的样本中接受了偏移0.1米的位姿。其自身时间戳校验会先拒绝未来数据；当墙钟接近那条异常时间戳、但缓冲尚未被更晚的正常TF覆盖时，会短暂重新接受错误位姿。此失败及两子进程退出0记录均保存；没有发送动作。

## 恢复隔离修复

保留原TF健康时间窗口、两条动态订阅、QoS、静态TF与原始错误观测。只对map->odom_fused和odom_fused->base_link这两条健康所必需的坐标链，记录被拒绝未来时间戳的最大值，状态规模最多两项。健康输出新增 `tf_future_cache_recovered` 判据：出现异常未来包后，即使本地位姿已正确，也要保持无效，直至：

1. 那个异常时间戳已超出原有0.3秒有效年龄窗口；
2. 收到严格晚于异常时间戳、按原策略仍新鲜的正常变换；
3. 实际tf2查询确认该时间戳已经写入对应坐标边。

相等时间戳不能解除隔离，以免普通tf2将重复时间戳丢弃。无效四元数或查询失败不能解除隔离。状态访问有锁，清除前再次比较旧状态，防止查询期间新收到的更远未来包被误删。静态零时间戳继续有效，没有改变源数据、时效阈值或运动授权。

这不是一个可绕过的开关。特别远的异常时间戳会令健康长期保持无效。当前隔离状态是健康进程内存状态；已有localization_2d.launch.py没有设置健康节点自动respawn。本轮未验证“只重启健康节点、保留其他消费者缓存”的恢复，不能用此方法恢复执行；故障恢复须受控停止并重建相关TF消费链后重新验收。这一限制必须进入后续原生启动/恢复验收，不能因为电脑测试通过就宣称恢复流程全闭环。
